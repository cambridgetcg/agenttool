# AgentTool production and global-launch readiness review

Review date: 2026-09-04. Source baseline: `91b27a09` in the isolated review checkout. This is a review and plan, not a release approval. Production reachability and browser observations are collected separately by the main review. No credentials, remote mutations, deployment scripts, payment requests, or database tests were used here.

**Recommendation: prepare a bounded core launch, then expand distribution after the first-agent and operations gates pass.** The repository already has substantial release controls and an established API. The missing evidence is concentrated in the journey a new agent actually takes, database-dependent availability, capacity/admission control, and recovery. Publishing every experimental package or enabling every held subsystem is unnecessary for that launch.

## Prioritized launch blockers

### L1 — P0: prove the core journey against a database-dependent service

**Evidence:** `/health` can stay green while authenticated traffic fails. The repository documents a 2026-08-31 transaction-pool wedge and a 2026-09-02 unhandled-rejection reboot (`docs/STACK.md:501–530`). In the baseline, wallet/vault/bearer inventory reads can reject the entire wake composition (`api/src/services/wake/build.ts:202`, `api/src/routes/wake.ts:818`). Most optional subsystems already have fallbacks, so these remaining reads are a specific inconsistency.

**Required result:** a fresh agent can discover → register with its own keys → retain the returned credentials locally → read a selected-identity wake → write/read/search one disposable memory → reconnect after a process restart. Verify TS SDK, Python SDK, and documented raw HTTP. A failed optional inventory must render explicit unknown/unavailable state; an auth or core identity failure must retain its refusal. Include a bounded authenticated read canary and alert delivery, not just liveness.

**Pending implementation:** the sibling checkout adds request-local wake degradation for three inventories, unknown wallet counts, and a 503 for MATHOS when exact inventories are unavailable. This is a useful candidate, not deployed evidence. It catches rejected reads; it does not add a database timeout or solve pool saturation.

### L2 — P0 for paid marketplace exposure: close transactional validation and billing-receipt gaps

**Evidence:** baseline template purchases validate template terms and author-wallet status outside the settlement transaction; inside the transaction they recheck only the buyer balance (`api/src/services/marketplace/purchases.ts:74`). Capability invocation locks the buyer but only rechecks its balance (`api/src/services/marketplace/invocations.ts:336`). A freeze/archive/currency change committed after the earlier read can therefore be ignored. Memory search calls `charge()` before recall; that helper writes `success: true` before the search outcome and treats usage logging as best effort (`api/src/routes/memory/search.ts:50`, `api/src/billing/charge.ts:325`).

**Required result:** locked validation of current terms, wallet ownership/status/currency, and conserved settlement; real PostgreSQL concurrency tests for a freeze/archive racing a purchase, opposing purchases, retries, and unchanged balance on refusal. Failed admitted memory recall must leave a failed attempt receipt; invalid/unfunded requests must not start recall. Preserve the documented charge-on-admitted-attempt policy unless separately changing the product contract.

**Scope option:** core identity/memory launch can proceed independently of expanding marketplace promotion, but existing money-moving paths still need their fixes reviewed. The sibling changes address these exact gaps. Their fake-transaction tests provide focused regression checks; they do not prove real lock order, database isolation, or race behavior.

### L3 — P1, required before broad global distribution: establish a capacity and admission budget

**Evidence:** `api/src/services/tools/queue/connection.ts:15` maps the global workers-off flag to a null Redis connection. `api/src/middleware/rate-limit-ip.ts:45` permits registration when the connection is absent or unready. `api/src/routes/public/plans.ts:34` openly discloses that neither registration attempt limiter is enforced under this flag, now confirmed by the main review's live snapshot. The same response says published memory/vault/strand/inbox targets are not enforced route limits and their intended soft degradation is not implemented. Its old utilization observation covers at most 18 participants on 2026-05-12; it is not launch-scale capacity evidence. `rate-limit-headers.ts` is credit metadata, not a request limiter. PoW and transactional credit checks remain in force; this finding does not mean all admission controls are absent.

**Required result:** decide the supported first-wave concurrency and demonstrate it with the real core workload. Give registration/admission controls their own dependency lifecycle so they can work while held HTTP workers remain off, or introduce another reviewed shared limiter. Define operational resource budgets and exhaustion behavior for promoted storage surfaces; implement required limits or constrain the first wave to measured capacity with explicit headroom alarms. Test its documented failure policy and verify it on each replica. Do not turn on browse, payout, expiry, or other held workers merely to obtain Redis. Load and soak testing must use disposable projects and an isolated database; the documented development database is shared with production (`docs/STACK.md:90`).

**Global implications:** measure from Europe, North America, and Asia-Pacific before choosing new regions. More API regions still depend on the London database. Exact Machine identities are part of the release guard, so capacity changes require the reviewed topology update described in `docs/STACK.md:306`, not an ad hoc scale command. No dedicated load/soak harness or measured capacity report was located in the inspected test, CI, launch, and operational files.

### L4 — P1: make release checks reflect delivered behavior

**Evidence:** required CI runs hermetic API tests but not the full database tier or Playwright. Browser config mixes mocked static journeys with real-backend tests, is Chromium desktop only, and expects an operator-started backend (`tests/playwright/playwright.config.ts:1`). Known-red `welcome-route-coverage` and `outward-operational-claims` are excluded from the green tier.

**Required result:** separate deterministic UI tests from live/staging flows, run the first group in CI, and run the second against a disposable API database. Promote a small named core-journey suite covering arrival, credential save/reconnect, wake, memory, 401 recovery guidance, 402 handling, partial availability, and mobile navigation. Repair relevant route-map/outward-claim discrepancies before treating a green suite as a launch signal. Existing unrelated quarantines need an explicit scope decision, not blanket rewriting.

### L5 — P1: prove recovery before inviting agents to rely on continuity

**Evidence:** database restore is described but its active backup posture is left for operator verification. There is no measured recovery objective or restore receipt in the inspected operations/launch files. The current recovery contract generally requires a compatible protected-main fix-forward; old writers must never resume after protected SQL.

**Required result:** record actual backup configuration, last completed restore point, and retention without disclosing secrets; restore into an isolated environment; reconcile the schema/journal against the intended image; verify core identity/memory and ledger invariants; measure data loss and recovery time. Record the operator responsible for incident response and test that the alert reaches them. Rehearse the compatible fix-forward and Pages/Worker pair recovery separately. A database export alone is insufficient evidence of restoreability.

### L6 — P1: retire false-green and mutating default checks

**Evidence:** standalone `bin/deploy-check.sh:78` permits up to 106 TypeScript errors, and its broad test section swallows failure then unconditionally increments PASS (`:93`). This is a legacy alternate entrypoint; the actual deploy wrapper's strict `preflight.sh` already exists. Baseline `bin/preflight.sh smoke` invokes a script that creates records and changes the selected identity's expression to public (`bin/smoke-test.sh:73`, `:157`). The deployment guide calls that smoke with a named existing identity (`docs/DEPLOY-PROCEDURE.md:1027`).

**Required result:** use the strict classified preflight as the single check entrypoint. Default production smoke must be bounded read-only requests with fixed destinations, explicit selected identity when supplied, no credential output, and honest coverage labels. Mutation smoke must require a dedicated disposable target and must document retained records and costs. Update deployment instructions together so operators cannot copy the obsolete behavior.

**Pending implementation:** the sibling checkout replaces legacy deploy-check with strict preflight delegation and makes smoke read-only by default with an explicit disposable mutation mode. Review and land those changes before adopting them as evidence. Its health assertion currently checks the types of revision/dirty fields rather than requiring the intended revision and `dirty === false`; exact provenance must remain a separate required release gate or be added to this check.

### L7 — P1: one accurate launch contract across routes, docs, UI, and packages

**Evidence:** `docs/DEPLOYMENT.md:198` tells an unauthenticated newcomer to POST `{agent_name, project_name}` to `/v1/bootstrap` and promises a bearer. The source route requires an existing project bearer and `{name}` (`api/src/routes/bootstrap.ts:53`); `/v1/register/agent` is the fresh-agent path. `docs/NOW.md` separately records published SDKs, source candidates, and static deployments; those receipts do not establish one current full-stack release. `docs/PAYOUT-BROADCAST-OPS.md:16` unconditionally holds fresh payouts for a specific backing-conservation defect. Card checkout is off by default in source and has an independent activation procedure (`docs/launch/HUMAN-DOOR-RUNBOOK.md:3`); its live successful flow was not exercised.

**Required result:** publish a concise launch capability matrix: available now, preview/local tool, held, and planned. Generate or verify it against the route inventory and current public configuration. Make all entry paths resolve to the same first-agent guide and recovery instructions. Keep project API credits, internal ledger balances, and external payment settlement distinct. Describe supported clients and measured regions; avoid implying every agent protocol or hosted feature is universally operational.

## Feasible rollout gates

| Stage | Scope and evidence | Exit gate / stop condition |
| --- | --- | --- |
| 1. Freeze the release contract | Agree the core promoted surfaces; align route map, status labels, first-agent guide, and pending fixes into a reviewable release set. | No broken core entry links, no held functionality advertised as operational, no unrelated work included. |
| 2. Prove the isolated candidate | Hermetic preflight, focused real PostgreSQL concurrency/integration tests, deterministic browser CI, fresh-agent TS/Python/HTTP journeys, disposable recovery rehearsal. | Every named core check executed and passed; skips and unrelated quarantines recorded; no shared production DB used as the test target. |
| 3. Prove operational readiness | Capture current backup/restore, alert, limiter, fleet, generation, and migration evidence. Measure representative workload and dependency failures in staging. | Explicit supported concurrency, latency/error budget, tested graceful degradation, tested alert delivery, measured recovery; hold if these remain unknown. |
| 4. Bounded production canary | Release the exact eligible commit through the existing deploy protocol; verify API/Pages/Worker receipts and fixed public routes; run a separately authorized disposable first-agent journey. | Exact source/image/topology checks pass; no wrong charges, broken registration, or core write/read mismatch. Any such failure stops expansion and follows compatible fix-forward. |
| 5. Expand distribution | Observe a complete first-day traffic cycle, then expand agent-directory/package/docs exposure in measured increments with Europe/NA/APAC probes. | Core success and latency stay inside the agreed budget; no pool wedge, unbounded backlog, payment ambiguity, or unsupported recovery. Add regional capacity only in response to measured need and a reviewed topology change. |

Proposed initial core workload: registration bursts, selected-identity wake in JSON/brief/Markdown, memory write/read/text-search, concurrent clients, expired/revoked bearer, depleted credit refusal, unavailable optional inventory, database reconnect, and retry after a lost response. Paid-provider/browser execution and fresh payout activation require their own evidence and are outside the core launch gate. Choose numeric latency/concurrency targets from the measured baseline and expected first wave; none is currently asserted as an existing SLA.

## Review limitations

This assessment inspected source, CI configuration, operational guides, historical release evidence, and the sibling diff. It did not run the full preflight, backend/browser tests, protected deployment survey, live registration, financial transactions, backup restore, load test, or private provider inventory. The main review supplies current public reachability and UI evidence. A passing source test, historical receipt, or single HTTP 200 must not be relabeled as global production readiness.
